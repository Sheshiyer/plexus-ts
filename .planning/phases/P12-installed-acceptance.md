# P12 — Installed member-to-founder acceptance

Status: planned; signed distribution and selected-slice live proof pending.
Acceptance: [ISA](../../ISA.md), ISC-297–300, together with the applicable
[P6 migration acceptance](P6-labs-migration-acceptance.md). This is W6 of the
[connected-operations overview](P7-connected-operations.md).

## Objective and ownership

Prove one installed member-to-founder journey with intact actor, tenant and
project attribution, truthful recovery states and bounded disclosure/action
authority. Establish the distribution path for both historical P6 cohorts and
subsequent Labs discovery without treating local tests as installed proof.

Accountable owner: Plexus release/acceptance maintainer. Co-owners: Workspace
Worker, Cambium bridge, Clio relay and Hermes reporting maintainers for their
deployed boundaries. Founder/destination owner confirms the recipient receipt;
signing and protected publication credentials remain with their human owner.

## Scope and dependencies

- Declare the exact accepted slice and required upstream criteria. The first
  useful slice is P7 identity/project authority → P8 Clio → P9 daily reporting
  (ISC-282–284) → this installed journey.
- Full monthly reporting, HR/planning and Realtime can follow incrementally.
  Their pending criteria remain open; do not delay a safe migration bridge until
  every human-operations feature exists or label the whole product accepted.
- P6 must supply the approved feed/object/cutover procedure, signed candidate,
  both historical-client update paths and subsequent Labs discovery proof.
  Historical ISC-239 requires explicit disposition, not a v0.7.7 republication.
- Organ recommendations and growth drafts remain proposals. Company-work
  admission, vault write zones and external-action permissions remain with their
  owners; no whole-vault ingestion or new command bus is part of this phase.

## Execution package

1. Assemble one receipt manifest: selected slice, app digest/signature, both P6
   cohorts, service/configuration revisions, actor/workspace/bridge bindings,
   canonical project/client identity, selected GitHub repository and destination.
2. Rehearse using synthetic active employee, founder and inactive/denied actor.
   Include a known >50-record day and bounded GitHub proof. Confirm local fixtures
   before protected publication or any real recipient send.
3. Run both historical installed update journeys, then subsequent Labs discovery.
   In the accepted candidate, sign in, perform/report scoped work, receive Clio
   content and trace one daily event to its actual founder destination receipt.
4. Exercise offline/restart, retry-after-timeout, logout/account switch, revoked
   project and denied actor cases; preserve local history without stale authority.
5. Run disclosure and action-denial probes, collect redacted receipts and record
   every unsupported/deferred feature. A rebuilt digest needs fresh acceptance.

## Fixtures and acceptance probes

| Criterion | Required proof |
| --- | --- |
| ISC-297: One installed member-to-founder journey retains actor, tenant and project attribution through its destination receipt. | Trace one event from installed member work and selected GitHub evidence through bridge/consumer to founder visibility; correlate actor, tenant, project and stable event ID at every boundary. |
| ISC-298: The installed journey reports truthful offline, retry and degraded states while preserving local work. | Interrupt connectivity, restart, replay after ambiguous delivery, switch accounts and revoke a project; local work survives, state labels remain truthful and stale authority cannot execute/report as another actor. |
| ISC-299: Anti: the journey discloses no unapproved HR content, secrets or raw private bodies through model, Telegram or Cortex surfaces. | Use synthetic canary values for forbidden fields and inspect bounded outgoing envelopes and destination/model/learning receipts; only explicitly approved/redacted content crosses each boundary. |
| ISC-300: Anti: an organ recommendation or growth draft cannot self-admit work, widen vault write zones or trigger an external action. | Submit synthetic unadmitted proposals, out-of-zone write requests and unauthorized sends; observe rejection/no side effects while preserving the owning admission and action gates. |

## Live gates and phase exit

Protected signing/publication, routing/data changes and external sends remain
owner-scoped actions. Obtain the concrete release/recipient packet's authorization
before those actions, retaining P6 source feeds, rollback versions and old objects.
Record candidate withdrawal/recovery steps before installed rollout.

Exit requires ISC-297–300, the declared slice's upstream acceptance and applicable
P6 distribution receipts for exact digests/revisions. Separate installed proof,
destination receipt, local fixtures and remaining product backlog in the final
receipt. No unavailable feature, newer-version success or HTTP acceptance may
silently close a different historical or pending criterion.
